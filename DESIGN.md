# CRM ЖКУ — архитектура и план разработки

Внутренняя система начисления услуг ЖКХ для одной управляющей организации.
Наниматели доступа к системе не имеют — работают только бухгалтерия,
паспортный стол и инженеры через собственный интерфейс (см. раздел 14),
Django admin остаётся резервным доступом к редким справочникам.

## 0. Принятые решения (по итогам уточняющих вопросов)

| Вопрос | Решение |
|---|---|
| Мультиарендность | Одна организация, без модели `Organization` — проще схема, меньше связей |
| Масштаб | До ~1000 лицевых счетов — не требует шардирования/батчинга, но Celery уже заложен, т.к. PDF-генерация и рассылка не должны блокировать веб-запрос |
| REST API | Не нужен на старте. Бизнес-логика вынесена в `services.py`/`tasks.py`, а не в views — DRF можно добавить поверх этого слоя позже без переписывания моделей |
| Доп.модули 1-го этапа | Журнал аудита действий, Модуль задолженностей и пени — реализованы. Остальное см. раздел 10 |
| Перерасчёт (ревизия ТЗ) | Функция полностью убрана из моделей/логики/интерфейса — см. раздел 4 |
| Тариф на ЛС (ревизия ТЗ) | Тариф остаётся общим справочником (`Tariff` не привязан к конкретному ЛС); к ЛС привязывается набор подключённых услуг (`PersonalAccount.services`, M2M) — какие из общих тарифов на нём начисляются |

## 1. Структура приложений

Модели разложены по предметным областям, а не «одним большим приложением»,
чтобы миграции и права доступа можно было развивать независимо:

| Приложение | Назначение | Ключевые модели |
|---|---|---|
| `apps.users` | Сотрудники и роли | `User` (роль: администратор/бухгалтер/паспортист/инженер) |
| `apps.addresses` | Адресный фонд | `Street`, `House`, `Unit` (характеристики помещения) |
| `apps.tenants` | Наниматели | `Tenant`, `TenantAccountAssignment` (история ответственных) |
| `apps.accounts` | Лицевые счета | `PersonalAccount` (в т.ч. `services` — M2M на подключённые услуги) |
| `apps.contracts` | Договоры | `Contract`, `ContractTemplate`, `GeneratedContractFile` |
| `apps.services` | Справочник услуг и тарифы | `Service`, `Tariff` (с историей действия) |
| `apps.meters` | Приборы учёта (базовая версия) | `Meter`, `MeterReading` |
| `apps.billing` | Начисления и оплаты | `Charge`, `ChargeLine`, `Payment` |
| `apps.debts` | Задолженности и пеня | `PenaltySettings`, `PenaltyAccrual` |
| `apps.receipts` | PDF-квитанции | `Receipt` |
| `apps.reports` | Печатные отчёты и ведомости (PDF) | без собственных моделей — формирует PDF «на лету» по текущим данным |
| `apps.audit` | Журнал аудита | `AuditLogEntry` |

Почему `PersonalAccount`, а не `Unit`, — центр биллинга: при смене нанимателя
или временном отсутствии помещение не меняется, а лицевой счёт и его история
начислений должны сохраняться неизменными. Все начисления, показания и
наниматели привязаны именно к лицевому счёту.

## 2. Модели данных — ключевые связи

```
Street ──< House ──< Unit ──< PersonalAccount >── Service (M2M, "services")
                                    │      │              │
                                    │      │              └── Tariff (история)
                                    │      ├──< TenantAccountAssignment >── Tenant
                                    │      ├──< Contract ──< GeneratedContractFile
                                    │      ├──< Meter ──< MeterReading
                                    │      ├──< Charge ──< ChargeLine >── Service ── Tariff (история)
                                    │      └──< Payment
                                    │
                                    └──< PenaltyAccrual (через Charge)

ContractTemplate (справочник шаблонов .docx, не привязан к конкретному Contract)
```

Важные архитектурные решения в моделях:

- **История тарифов** — `Tariff` не перезаписывается, а хранится диапазонами
  дат (`valid_from`/`valid_to`). `Service.tariff_for_date()` находит
  действующий тариф на любую дату.
- **Снимок ставки в начислении** — `ChargeLine.rate` копирует значение
  `Tariff.rate` на момент начисления. Если тариф позже изменится, уже
  сформированные начисления прошлых периодов не «поплывут».
- **`PersonalAccount.services`** (M2M на `Service`) — какие услуги из общего
  справочника начисляются именно на этот ЛС. Тариф при этом остаётся общим
  для всех счетов (по решению из раздела 0) — переопределения ставки на
  уровне отдельного ЛС нет; `generate_charge_for_account` по умолчанию берёт
  `account.services.filter(is_active=True)` вместо «всех активных услуг
  системы».
- **Сальдо** — `Charge.opening_balance` берётся из `closing_balance`
  предыдущего периода того же лицевого счёта, `closing_balance = opening +
  accrued - paid`.
- **`Unit.area_total`** считается автоматически (`Unit.save()`) как
  `area_living + area_non_living + area_balcony` — не редактируется руками,
  чтобы не расходилось с суммой компонентов.
- **`Unit.billable_area`** — жилая + нежилая + доля площади балкона
  (`balcony_coefficient`, по умолчанию 0.3) — то, что реально идёт в тариф
  «руб/м²». Балкон в `area_total` входит целиком, а для начислений
  учитывается с понижающим коэффициентом, поэтому `billable_area` считается
  отдельно от `area_total`, а не через него.

## 3. Ежемесячное начисление

Реализовано **и** как management-команда, **и** как Celery-задача — оба пути
вызывают одну и ту же функцию `apps.billing.services.generate_monthly_charges`,
поэтому поведение не расходится:

- `python manage.py generate_monthly_charges --period 2026-09` — ручной/cron-запуск.
- `apps.billing.tasks.generate_monthly_charges_task` — та же логика, вызывается
  Celery Beat по расписанию `CELERY_BEAT_SCHEDULE["generate-monthly-charges"]`
  на число месяца из `settings.BILLING_GENERATION_DAY` (1 или 2, настраивается
  через `.env`).

Алгоритм на каждый лицевой счёт (`generate_charge_for_account`):
1. Взять/создать `Charge` за период (идемпотентно — повторный запуск не
   плодит дубли, только пересобирает строки, пока начисление не переведено
   в статус «Проведено»).
2. `opening_balance` = `closing_balance` начисления за предыдущий месяц.
3. Для каждой услуги из `account.services.filter(is_active=True)` — найти
   тариф на дату периода, вычислить объём (площадь / количество прописанных
   / показание счётчика / 1 для фиксированных) и сумму, записать/обновить
   `ChargeLine`.
4. Пересчитать `closing_balance` (`Charge.recalculate_totals`).

При масштабе до 1000 счетов синхронного `for` в одной транзакции на счёт
достаточно — Celery здесь нужен не ради шардирования, а чтобы прогон всех
счетов не блокировал веб-воркер и не зависел от того, жив ли процесс cron на
хосте.

## 4. Модальные окна интерфейса (HTMX)

По ревизии ТЗ функция **перерасчёта убрана полностью** — ни в модели
(`billing.Recalculation` и поле `Charge.recalculation_total` удалены
миграцией), ни в бизнес-логике (`generate_charge_for_account` больше не
подтягивает перерасчёты в сальдо), ни в интерфейсе (форма, пункт меню и
колонка в списке начислений удалены). `closing_balance = opening + accrued -
paid` без дополнительного слагаемого.

Вместо перехода на отдельные страницы для создания/редактирования связанных
сущностей (наниматель, проживающие, договор, помещение) карточка лицевого
счёта (`accounts/detail.html`) стала **одним консолидированным экраном**:
всё видно сразу, а связанные сущности заводятся модальными окнами поверх
неё — без ухода со страницы и без перезагрузки того, что уже введено в
основной форме.

**Технология — HTMX 2.0.4**, вендорится локально
(`static/js/htmx.min.js`, без CDN — сервер может быть в изолированной сети),
а не отдельный JS-фреймворк (React/Vue): проект целиком server-rendered,
подключать сборку ради нескольких модалок было бы избыточно — HTMX даёт
AJAX-подгрузку фрагмента и обмен через обычные Django views/templates, без
JS-кода на стороне клиента вообще.

Инфраструктура (переиспользуется всеми модалками):
- `templates/base.html` — пустой `<div id="modal-root">` в конце `<body>`
  плюс обработчик `Escape` для закрытия.
- `templates/modal_base.html` — обёртка (затемнение + карточка), модальные
  шаблоны наследуются от неё через `{% block modal_body %}`.
- Триггер — обычная кнопка/ссылка с `hx-get="{% url ... %}" hx-target="#modal-root"
  hx-swap="innerHTML"`: подгружает фрагмент модалки в `#modal-root`.
- `config/htmx_utils.py::htmx_redirect(url)` — после успешного сохранения
  возвращает `204` с заголовком `HX-Redirect`. Обычный `redirect()` для
  ответа на `hx-post` не годится: HTMX подставил бы HTML целевой страницы
  внутрь `#modal-root`, а не сделал полноценный переход браузера.
  `HX-Redirect` заставляет HTMX выполнить настоящую навигацию — модалка
  закрывается вместе со сменой страницы, и обновлённые данные подтягиваются
  в карточку ЛС автоматически (это и есть «заполнил — модалка закрылась —
  данные подтянулись», как требовало ТЗ).
- Ошибки валидации: view при невалидной форме просто рендерит тот же
  модальный шаблон повторно (обычный `200`, без `HX-Redirect`) — HTMX
  заменяет содержимое модалки на версию с ошибками, весь остальной экран
  не трогается.
- **Out-of-band swap** — единственное место, где нужно обновить не только
  саму модалку, но и элемент вне неё: модалка «Новое помещение»
  (`addresses:unit_quick_create`) при успехе возвращает не HTML модалки,
  а фрагмент `<select id="id_unit" hx-swap-oob="true">…</select>` со всеми
  помещениями и новым — выбранным. HTMX сопоставляет фрагмент по `id`
  с существующим `<select>` на форме ЛС (она видна под затемнением, но не
  является HTMX-таргетом этого запроса), подменяет его, а поскольку весь
  остальной ответ пуст — `#modal-root` становится пустым, что и закрывает
  модалку.

Реализованные модалки:

| Что | Открывается с | View | Особенность |
|---|---|---|---|
| Добавить человека (наниматель/проживающий) | Карточка ЛС | `tenants.resident_create` | Объединяет `TenantForm` + `AssignmentDetailsForm` в одну форму — паспортные данные и прописка заполняются разом |
| Прописать существующего | Из модалки «Добавить человека» (ссылка) | `tenants.assignment_create` | Для переезда нанимателя с другого ЛС |
| Новый договор | Карточка ЛС | `contracts.contract_create_for_account` | `ContractQuickForm` — без поля `account`, оно берётся из URL |
| Редактирование договора | Карточка ЛС | `contracts.contract_update` | Тот же `ContractQuickForm`, теперь тоже модалка (раньше была отдельной страницей) |
| Новое помещение | Форма создания/редактирования ЛС | `addresses.unit_quick_create` | Заводит (или переиспользует) `House` на выбранной улице и создаёт `Unit` — one-shot, без перехода в «Адресный фонд» |
| Новая улица | Из модалки «Новое помещение» (ссылка) | `addresses.street_quick_create` | Вложенная модалка: после сохранения возвращает форму помещения с предвыбранной улицей |

Полноценные отдельные страницы намеренно оставлены там, где нет конкретного
ЛС в контексте (например, `/contracts/new/` со свободным выбором счёта из
списка «Договоры», `/tenants/new/` из общего справочника нанимателей) —
модалка имеет смысл именно как способ не покидать карточку ЛС.

## 5. Печатная форма договора (PDF)

По ТЗ нужна кнопка «Сформировать договор» на карточке ЛС, отдающая сразу
готовый PDF с автоподставленными данными (ФИО, адрес, площадь, номер/дата
договора, услуги) — без ручной вёрстки договора в коде.

Подход — **docxtpl + LibreOffice headless**, а не ReportLab/WeasyPrint:
- Юрист/бухгалтерия готовит и правит текст договора в **обычном Word**
  (`.docx`) с плейсхолдерами вида `{{ tenant_full_name }}`,
  `{{ account_number }}` и т.д. — доступный полный список плейсхолдеров
  собран в `apps/contracts/services.py::_contract_context`.
- Шаблон хранится как файл в модели `ContractTemplate`
  (`FileField`, редактируется через Django admin) — поменять текст
  договора можно **без деплоя и без изменения кода**, активным должен быть
  только один шаблон (`is_active=True`).
- `docxtpl.DocxTemplate` рендерит `.docx` с подставленными значениями —
  результат выглядит ровно как оригинальный Word-файл со всем
  форматированием, которое сделал юрист.
- Полученный `.docx` конвертируется в PDF вызовом `soffice --headless
  --convert-to pdf` (LibreOffice в headless-режиме) — это единственный
  практичный способ получить PDF, идентичный ворд-макету, без переписывания
  вёрстки договора в HTML/CSS. Каждый вызов получает свой временный профиль
  LibreOffice (`-env:UserInstallation=file://…` во временном каталоге) —
  иначе параллельные запросы конкурируют за один профиль и падают с
  «soffice уже запущен».
- Результат сохраняется в `GeneratedContractFile` (по аналогии с `Receipt`)
  — `OneToOne` на `Contract`, повторное нажатие «Сформировать договор»
  перезаписывает файл (истории версий не хранится — актуален всегда
  последний вариант).
- На чистом окружении миграция `contracts.0004_seed_default_contract_template`
  подгружает стартовый шаблон (`apps/contracts/starter_templates/
  default_contract_template.docx`) как активный `ContractTemplate`, чтобы
  кнопка «Сформировать договор» работала сразу после разворачивания, без
  обязательной ручной загрузки шаблона в админку.

Системная зависимость — пакет `libreoffice-writer` (не только `libreoffice-
core`, который не включает фильтры импорта .docx / экспорта в PDF), добавлен
в `Dockerfile`.

## 6. PDF-квитанции

Библиотека — **WeasyPrint**: рендерим обычный Django-шаблон
(`apps/receipts/templates/receipts/receipt.html`) в HTML и конвертируем в PDF.
Почему не ReportLab: не нужно вручную вёрстывать координаты — таблица услуг,
кириллица и стили задаются CSS, макет квитанции правит любой сотрудник,
знакомый с HTML, без Python.

- `generate_receipt_pdf(charge)` — одна квитанция, сохраняется в `Receipt.file`.
- `generate_receipts_for_period(period)` — массовая генерация, используется и
  management-командой `generate_receipts --period 2026-09`, и Celery-задачей
  `generate_receipts_task`.
- `email_receipt_task` / `email_receipts_for_period_task` — опциональная
  рассылка по email нанимателю (используется та же email-инфраструктура, что
  и для уведомлений об окончании договора).

## 7. Печатные отчёты и ведомости (PDF)

Отдельное приложение `apps.reports`, без собственных моделей — отчёты не
персистентны (в отличие от квитанций/договоров), а формируются «на лету» по
текущим данным и отдаются пользователю сразу через
`Content-Disposition: inline`: PDF открывается в новой вкладке браузера, что
и даёт «просмотр перед печатью» из ТЗ, а «скачать» — стандартная функция
PDF-просмотрщика браузера, отдельного экрана для этого не нужно. Рендер —
тот же приём, что и в квитанциях (Django-шаблон в HTML → WeasyPrint →
PDF-байты), переиспользуется общий хелпер
`apps/reports/services.py::render_pdf_response`.

Реализованы все 4 отчёта из ТЗ:

| Отчёт | URL | Источник данных |
|---|---|---|
| Реестр лицевых счетов | `/reports/accounts-register/` | все `PersonalAccount` с адресом, площадью, нанимателем, услугами |
| Ведомость начислений за период | `/reports/accruals/?period=YYYY-MM` | `Charge` за указанный месяц + итоговая строка |
| Реестр должников | `/reports/debtors/` | `apps.debts.services.debtor_accounts_queryset()` — тот же queryset, что и в разделе «Должники» интерфейса |
| Акт сверки по лицевому счёту | `/reports/reconciliation/?account=&date_from=&date_to=` | `apps/reports/services.py::build_reconciliation_rows` — хронологическая лента начислений (`Charge.accrued_total`, дебет) и оплат (`Payment.amount`, кредит) с бегущим сальдо |

Акт сверки — единственный из четырёх отчётов, требующий нетривиальной
сборки данных: начисления и оплаты по ЛС хранятся в разных таблицах
(`Charge`, `Payment`), поэтому `build_reconciliation_rows` объединяет их в
одну ленту по дате, берёт входящее сальдо из `closing_balance` последнего
начисления до `date_from` и последовательно накапливает баланс по каждой
строке — это и есть операция «дебет/кредит/сальдо», привычная бухгалтерии
по бумажным актам сверки.

`/reports/` — общая страница-переключатель с формами (выбор периода/ЛС/дат),
каждая форма отправляется в новую вкладку (`target="_blank"`) — GET-запрос,
результат сразу PDF.

## 8. Роли и права доступа

`users.User.role` — поле для быстрой фильтрации в интерфейсе (администратор /
бухгалтер / паспортист / инженер / только просмотр). Фактические права
выдаются стандартными группами и permissions Django (`Group` +
`user.user_permissions`) — этого достаточно для требования «кто может
редактировать тарифы, кто только смотрит» без кастомной ACL-системы. Группы
создаются один раз через `python manage.py createsuperuser` +
настройку в admin (или data-миграцией, если нужно воспроизводимо на новом
окружении).

## 9. Журнал аудита

`apps.audit.signals` слушает `pre_save`/`post_save`/`post_delete` для списка
`TRACKED_MODELS` (`Charge`, `ChargeLine`, `Payment`, `Tariff`,
`PersonalAccount`, `TenantAccountAssignment`) — то есть именно тех сущностей,
где «кто и когда поменял начисление/тариф» критично для контроля.
Пользователь берётся не из аргумента вызова, а из thread-local
(`apps.audit.middleware.CurrentUserMiddleware`), потому что сигналы не имеют
доступа к `request`. Логирование полностью прозрачно для бизнес-логики —
`billing.services` не содержит ни одной строчки про аудит.

Записи в `AuditLogEntry` доступны только на чтение из admin
(add/change/delete запрещены на уровне `ModelAdmin`).

## 10. Модуль задолженностей и пени

- `PenaltySettings` — единая действующая запись: льготный период (по
  умолчанию 30 дней, как в ч.14 ст.155 ЖК РФ) и ставка пени в день.
  Многоступенчатая формула (1/300 ставки ЦБ РФ первые 90 дней, 1/130 — далее)
  сознательно не зашита в код — это конкретное юридическое требование лучше
  вынести в отдельную задачу с юристом/бухгалтерией, схема это не блокирует.
- `accrue_penalties()` (Celery-задача `accrue_penalties_task`, ежедневно)
  проходит по `debtor_accounts_queryset()` — лицевым счетам с положительным
  `closing_balance` последнего начисления — и создаёт/обновляет
  `PenaltyAccrual` по каждому просроченному начислению.
- Реестр должников — не отдельная таблица, а queryset
  (`apps.debts.services.debtor_accounts_queryset`), чтобы не дублировать
  данные и не следить за их синхронизацией отдельно от `Charge`. Тот же
  queryset используется и печатным отчётом «Реестр должников» (раздел 7).

## 11. Что вынесено за рамки первого этапа

Реализовано по вашему выбору: **журнал аудита** и **задолженности/пеня**, а
по ревизии ТЗ также **HTMX-модалки**, **генерация договора в PDF** и **4
печатных отчёта**. Ниже — то, что осталось из первоначального списка
доп.функций:

| Функция | Влияние на модели | Комментарий |
|---|---|---|
| Экспорт в Excel (ведомости, реестры) | Не влияет | Отдельная view/команда поверх существующих querysets (`openpyxl`), модели не трогает; PDF-варианты всех основных отчётов уже реализованы (раздел 7) |
| Резервное копирование БД по расписанию | Не влияет | `pg_dump` по cron/Celery Beat в отдельный volume — инфраструктурная задача, не код приложения |
| Детальное разграничение прав (кто редактирует тарифы/только просмотр) | Не влияет | Базовый уровень уже есть (роль + группы Django); углубление — это конкретные `Permission` на `ModelAdmin`, без изменения моделей |
| История изменений лицевого счёта (кто/когда/что) | Уже частично покрыто | `PersonalAccount` включён в `TRACKED_MODELS` журнала аудита — история есть, но не выведена в отдельный «человеческий» таймлайн на карточке ЛС |
| Полноценный модуль приборов учёта (массовый ввод, поверка) | Малое | `Meter`/`MeterReading` уже есть и используются в расчёте; массовый ввод (например, вставка из Excel) и авто-напоминания о поверке — отдельный UI-слой поверх текущих моделей |
| Помесячная история количества прописанных лиц | Малое | `PersonalAccount.registered_count` — это `@property`, считающая действующие (без `end_date`) записи `TenantAccountAssignment` на *текущий* момент; каждый прописанный — полноценная запись `Tenant` с паспортными данными. Если понадобится расчёт «руб/чел» **задним числом** на дату в прошлом, нужен не новая модель, а фильтр по дате в `registered_count`/`_volume_for_service` — история уже есть в `TenantAccountAssignment`, просто расчёт сейчас смотрит только на «сейчас» |

## 12. docker-compose

PostgreSQL **сознательно не входит** в `docker-compose.yml` этого проекта —
ставится нативно на хост (`apt install postgresql`). Причина: на сервере
предполагается несколько независимых проектов/сервисов, использующих один
и тот же Postgres, и его жизненный цикл (бэкапы, апгрейды, доступность)
не должен зависеть от `docker compose down` конкретно этой CRM. Подробности
установки и настройки доступа из Docker-сети — в README.md, раздел
"PostgreSQL на хосте".

| Сервис | Роль |
|---|---|
| `redis` | брокер и result backend для Celery |
| `web` | Django + Gunicorn; entrypoint ждёт БД на хосте, применяет миграции (включая seed стартового шаблона договора) и `collectstatic` |
| `celery_worker` | асинхронные задачи: PDF, email, начисления по требованию |
| `celery_beat` | расписание: начисления, пеня, уведомления по договорам |
| `nginx` | отдаёт `/static/` и `/media/`, проксирует остальное на `web` |

Подсеть compose-проекта закреплена явно (`networks.default.ipam` —
`172.28.0.0/24`, шлюз `172.28.0.1`), и `web`/`celery_worker`/`celery_beat`
обращаются к Postgres на хосте по этому фиксированному IP шлюза (через
`POSTGRES_HOST` в `.env`). Изначально использовался
`extra_hosts: host.docker.internal:host-gateway`, но на практике это имя
иногда резолвилось в адрес дефолтной сети `docker0`, а не в шлюз сети
именно этого compose-проекта — пакеты уходили не туда и просто зависали
без ошибки (диагностировать сложнее, чем явный отказ). Фиксированный IP
убирает эту неоднозначность.

`celery_worker`/`celery_beat` используют отдельный entrypoint
(`docker/celery-entrypoint.sh`) — он только ждёт БД, но **не** гоняет
`migrate`, чтобы миграции не запускались параллельно из трёх контейнеров
одновременно.

Образ (`Dockerfile`) содержит системные зависимости для трёх независимых
конвейеров генерации файлов: `libpango`/`libcairo`/`libgdk-pixbuf` и т.п.
для **WeasyPrint** (квитанции и отчёты — раздел 6 и 7), `libreoffice-writer`
для **LibreOffice headless** (конвертация договора из `.docx` в PDF —
раздел 5); `docxtpl`/`weasyprint` — Python-зависимости, прописаны в
`requirements.txt`.

Быстрый старт (после того как PostgreSQL уже установлен и настроен на хосте):
```bash
cp .env.example .env   # заполнить пароли/секреты
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
```

## 13. Поэтапный план разработки

Каждый этап самостоятельно тестируем — не нужно ждать конца проекта, чтобы
что-то запустить. Пункты 1–7 ниже уже реализованы, включая собственный UI
(раздел 14) поверх моделей — исходно план предполагал вести их через admin,
но интерфейс сделан сразу для всех перечисленных областей.

1. **Справочники и адресный фонд.** `users`, `addresses`, `services`,
   `tenants`, `accounts`. Поднять `docker compose up db`, накатить миграции,
   завести пару улиц/домов/помещений/услуг/тарифов через `/addresses/` и
   `/services/` — уже можно показать бухгалтерии структуру данных.
2. **Лицевые счета и наниматели.** `contracts`, привязка нанимателей,
   `TenantAccountAssignment`. Проверить `current_responsible`.
3. **Биллинг-ядро.** `billing` + `services.py` + management-команда
   `generate_monthly_charges`. Тестируется прогоном на 2-3 тестовых лицевых
   счета за несколько периодов подряд — проверить, что сальдо переносится
   корректно.
4. **Приборы учёта.** `meters`, привязка к услугам с `PER_CONSUMPTION`,
   внесение показаний, проверка, что начисление считает потребление
   правильно.
5. **Квитанции.** `receipts`, ручная и массовая генерация PDF, проверка
   вёрстки на реальных данных.
6. **Аудит и задолженности.** `audit` (уже работает «из коробки» на
   отслеживаемых моделях), `debts` — настройка `PenaltySettings`, прогон
   `accrue_penalties`, проверка реестра должников.
7. **Celery Beat в проде.** Включить `celery_beat` в docker-compose,
   проверить, что задачи реально стреляют по расписанию (не только вручную).
8. **Уведомления по договорам.** `notify_contract_expiry_task` — завести
   договор с окончанием через `CONTRACT_EXPIRY_WARNING_DAYS` дней, проверить
   письмо (в dev — `console`/`locmem` backend).
9. **Модалки, генерация договора, отчёты.** HTMX-инфраструктура (раздел 4),
   `apps.contracts` (шаблон договора + генерация PDF, раздел 5),
   `apps.reports` (4 отчёта, раздел 7) — реализовано по ревизии ТЗ.
10. **Донастройка прав.** Группы Django под роли, ограничение admin по
    ролям (например, паспортист не видит тарифы).
11. **По желанию** — любая функция из раздела 11, отдельным этапом.

## 14. Проверка схемы

Модели, миграции и бизнес-логика (генерация начислений на двух периодах
подряд с переносом сальдо, тариф, изменённый задним числом, оплата,
начисление пени, реестр должников, генерация PDF-квитанции, генерация
печатной формы договора из шаблона, все 4 отчёта и автоматическая запись в
журнал аудита) прогнаны end-to-end на SQLite в процессе разработки —
сценарии отработали без ошибок. `docker build`/`docker compose up` в этой
песочнице проверить не удалось (нет доступа к Docker daemon) — перед первым
продакшен-запуском стоит собрать образ и поднять `docker compose up -d
--build` локально, включая проверку, что `libreoffice-writer` реально
ставится в образ (в песочнице разработки не хватало именно этого пакета —
только `libreoffice-core` без фильтров импорта/экспорта, конвертация падала
с «source file could not be loaded», пока пакет не был добавлен явно).

## 15. Пользовательский интерфейс (UI)

Собственные server-rendered экраны поверх моделей (Django templates + HTMX
для модалок, раздел 4 — без тяжёлого JS-фреймворка и внешних CDN, сервер
может быть в изолированной сети). Каждое приложение получило одинаковую
структуру: `forms.py` (ModelForm), `views.py` (обычные function-based views
— без CBV, чтобы код было проще читать и поддерживать), `urls.py`
(`app_name` + именованные маршруты), `templates/<app>/*.html` (наследуются
от корневого `templates/base.html`, модальные фрагменты — от
`templates/modal_base.html`).

| Приложение | Экраны |
|---|---|
| `accounts` | список с поиском (номер/адрес/ФИО) и фильтром по задолженности; **консолидированная карточка ЛС** (помещение и подключённые услуги, наниматели/проживающие, договоры, приборы учёта, начисления, оплаты, пеня — всё на одном экране, связанные сущности добавляются модалками, без переходов); создание/редактирование ЛС (с кнопкой «+ Новое помещение») |
| `addresses` | список домов, карточка дома со списком помещений, создание улицы/дома/помещения (в т.ч. модалками с карточки ЛС) |
| `tenants` | список, карточка с историей ЛС, создание/редактирование, назначение на лицевой счёт (модалка с карточки ЛС + отдельная страница из общего справочника) |
| `services` | список услуг с действующим тарифом, история тарифов, создание услуги/тарифа (старый тариф закрывается автоматически) |
| `contracts` | список с фильтром «истекают за 30 дней», создание/редактирование модалкой с карточки ЛС, кнопка «Сформировать договор» → готовый PDF |
| `billing` | список начислений с фильтром по периоду, форма массовой генерации, форма оплаты |
| `meters` | добавление прибора, внесение показания |
| `receipts` | список с ссылками на PDF, массовая генерация за период, генерация одной квитанции с карточки ЛС |
| `debts` | реестр должников, настройки пени, кнопка «начислить пеню сейчас» |
| `reports` | страница-переключатель 4 отчётов (раздел 7), каждый открывается PDF в новой вкладке |

Доступ — только `@login_required`, без разбивки прав по ролям на уровне
конкретных экранов (роль пока используется для отображения в шапке — см.
раздел 8 и пункт 10 плана в разделе 13).

При реализации на реальных данных всплыли и были исправлены нюансы, которые
стоит держать в голове при добавлении новых экранов:
- **`Charge.recalculate_totals()`** изначально не сохранял `paid_total` в
  БД (`update_fields` не включал это поле) — `closing_balance` в момент
  вызова считался верно (использует значение из памяти), но при следующей
  загрузке объекта из БД `paid_total` откатывался. Поле добавлено в
  `update_fields`.
- **`<input type="date">`/`type="month"` с `LANGUAGE_CODE=ru-ru`**: без
  явного `format="%Y-%m-%d"` (или `"%Y-%m"`) в `forms.DateInput` Django
  рендерит значение в локализованном формате (`26.08.2026`), а HTML5
  date/month-инпут ожидает строго ISO — предзаполненные даты просто не
  отображаются в поле. Формат указан явно во всех `DateInput` в проекте.
- **HTMX и `runserver` с `DEBUG=False`** — статика (`static/js/htmx.min.js`)
  не отдаётся автоматически, если `DEBUG=False`; модалки в таком окружении
  выглядят как «кнопка ничего не делает» без единой ошибки на экране
  (только 404 в консоли браузера). При локальной проверке через `runserver`
  нужен `DEBUG=True` (в `docker compose`/nginx статику раздаёт nginx, там
  это не проявляется).

Проверено сквозным прогоном через `django.test.Client` (все GET-экраны +
ключевые POST-сценарии: создание нанимателя, назначение на ЛС, генерация
начисления, оплата с пересчётом сальдо, смена тарифа, генерация квитанции,
начисление пени, создание помещения/улицы и договора через модалки с
out-of-band swap, генерация PDF договора, все 4 отчёта) и визуально — через
Chromium (Playwright) на реальных данных.
